2026-10-21，实物 ATSAMR21G18A，ST-Link V2，SWD 1 MHz。

```
023efc81fb12f6bbfec844374120924c8c1e8597ea3e2884af3306df3d8639c8
```

全片按 1024 行覆盖检查，其中 395 行重新擦写；其余 629 行原本全 FF，与备份一致，未重复擦除。另有前置单行试写一次。因此这次已经验证了实际编程及启动区写回能力。

原固件恢复运行后会自行改变配置行 `0x3F800..0x3F8FF` 的运行时字段，本轮差异仍仅在 `0x3F890`。上述完整 SHA-256 是**烧录后、恢复运行前**的校验结果；以后重新运行原固件再备份，全片哈希可能不同。这个字节的完整语义仍未确认。

## 烧录工具

`samr21_swd_flash.py` 使用 pyOCD 控制 ST-Link，经 SWD 直接操作 SAMR21 的 NVMCTRL。擦除/写入几何和命令来自用户提供的 Microchip.SAMR21_DFP.2.1.155 设备包：`scripts/dap_cortex-m0plus.py` 与 `ATSAMR21G18A.atdf`。采用手动写页（MANW、ER/PBC/WP）并关闭编程期间的 Flash 缓存。

这条通路已实测，不依赖 Keil 的 FLM。现有 Keil 编译器可以用于后续固件编译，生成的固件烧录需要再增加相应镜像入口；当前脚本严格限定写回本机这份原厂备份。

脚本只允许擦写普通 Flash 地址 `0x00000000..0x0003FFFF`。不执行整片 DSU 擦除，不更改熔丝、锁位、校准区或 ST-Link 固件。遇到芯片保护、BOOTPROT 或启用的看门狗会停止。

## 以后再次恢复原厂

保持 ST-Link 与板卡供电、SWD 连接正常，关闭占用该 ST-Link 的其他调试器。在恢复包目录打开 PowerShell：

```powershell
# 读取并检查，包含复位停机与双份备份，不写 Flash：
.\恢复原厂.ps1 -InspectOnly

# 原厂状态下再次写回完整原厂备份：
.\恢复原厂.ps1

# 以后刷过自制程序，或当前 Flash 已不同，明确覆盖为原厂备份：
.\恢复原厂.ps1 -AllowNonOriginal
```

启动脚本优先使用本任务已经验证的 Python 环境，或恢复包旁的 `.venv`；均不存在时，尝试使用本机 Python 创建隔离环境并安装 `flash_requirements.txt`。首次建立环境需要可用的 Python 和网络。Windows ST-Link 驱动本次已经装好。

每次运行都创建新的 `flash_runs/<唯一编号>/`，保存写入前两份 Flash 备份、辅助区前后备份和 `result.json`；不会覆盖以前的记录。恢复时如当前内容不同，所有与原厂备份不同的行也纳入擦写，包括原厂备份中应为 FF 的区域。

`-AllowNonOriginal` 路径会先在复位入口停机，使用制造商的 DEMCR.VC_CORERESET、SYSRESETREQ、DHCSR.C_HALT、DSU.CRSTEXT 流程，不依赖当前程序内的函数地址。实测在原始复位入口 `PC=0xAA0` 成功停机；随后在该复位状态下也完成了一次单行擦写、全片校验、原固件启动与刷新检查。

若将来出现固件混合状态的恢复失败，工具会保持 CPU 停机并保留记录；需要排查连接或供电后再次运行恢复命令。自制固件尚未写入，所以“从自制固件恢复”这一完整场景尚未实测；已验证的是所需的直接复位停机、普通 Flash 编程和原厂启动能力。
